# Проверка готовности к production

Дата: 8 октября 2026 года. Проверенный коммит: `63bba34` (ветка `master`).

## Вердикт

**Для публичного production проект пока не готов.** Основа пригодна для небольшого сервиса расписания, но перед публикацией нужны исправления безопасности, устойчивости ботов и эксплуатационные проверки. После исправлений можно запускать один экземпляр на домашнем сервере с умеренной нагрузкой. Гарантировать число одновременных пользователей без измерений нельзя.

Проверены Java-код, шаблоны и JavaScript, настройки Spring, миграции, тесты, GitHub Actions и файлы деплоя. `.codegraph/` отсутствует. Реальные токены и пароли из `.env` не выводились. Настройки сервера, маршрутизатора и работа настоящих ботов не проверялись. Код приложения не изменён.

## Блокеры и исправления

### 1. CSRF отключён для административного API — высокий приоритет

`src/main/java/ru/ugk/schedule/config/SecurityConfig.java:48` исключает `/api/**` из CSRF. Административный API использует браузерную сессию, а не отдельный bearer token. `static/js/admin-schedule.js` не передаёт CSRF token.

Конкретный межсайтовый exploit не подтверждён: JSON Content-Type, CORS/preflight и поведение SameSite ограничивают некоторые сценарии. Однако эти ограничения не заменяют CSRF-защиту для операций с session cookie.

Исправление: оставить исключения только для двух публичных POST `/api/public/telegram/group` и `/api/public/max/group`. Передавать CSRF token из Thymeleaf в заголовок каждого изменяющего запроса административного JavaScript. Проверить: POST/PUT/DELETE без токена дают 403, с действительной сессией и токеном работают. Отдельно проверить обычные формы каталога.

### 2. Небезопасные значения по умолчанию — высокий приоритет

`application.properties:13–14,20–21`, `AdminBootstrapConfig.java:17–24`: допускаются `postgres/postgres` и `admin/admin123`. При пустой новой БД отсутствие настройки создаёт известного администратора. После создания изменение `APP_ADMIN_PASSWORD` не меняет сохранённый BCrypt hash.

Исправление: проверять production-конфигурацию до запуска, отклонять пустые/стандартные пароли и шаблонные значения. До первого старта назначить отдельного пользователя БД и случайный пароль администратора. Для существующей БД нужен отдельный безопасный механизм смены пароля; не рассчитывать на редактирование `.env`.

### 3. Нет ограничений злоупотребления — высокий приоритет публичного запуска

В приложении и `deploy/nginx.conf` нет rate limit входа и публичного API. BCrypt делает перебор дорогим для сервера. Объём JSON проверяется уже после чтения тела: лимит 16384 символа в валидаторе не ограничивает объём HTTP body целиком.

Исправление: ограничить частоту логина и API на reverse proxy, задать `client_max_body_size`, таймауты и бюджет соединений. Для админки предпочтителен доступ через LAN/VPN. Лимит по IP учитывать с запасом: весь колледж может выходить через один NAT. При прокси/туннеле доверять real IP только от явно разрешённого upstream.

### 4. Надёжность ботов — высокий приоритет

`TelegramBotService.java:32,37–46`, `MaxBotService.java:34–49,164–183`:

- Оба `@Scheduled` используют общий scheduler. При текущей конфигурации Spring Boot использует один поток. Медленный MAX задерживает Telegram и наоборот.
- В Telegram нет явно настроенных connect/read timeouts. Серверный `getUpdates?timeout=1` не ограничивает все сетевые операции клиента.
- Обработка последовательная. MAX удаляет сообщения с паузами 550 мс прямо внутри обработки события.
- Telegram обновляет offset до успешной обработки; ошибка теряет неуспешное событие. Остаток пачки прерывается и может прийти на следующем запросе.
- MAX обновляет marker до обработки пачки; ошибочные события пропускаются.
- Offset/marker не сохраняются между перезапусками. Нет устойчивой очереди, идемпотентности и обработки 429 с Retry-After.

Минимум: отдельные потоки ботов (`spring.task.scheduling.pool.size=2`), явные HTTP timeouts, ограниченные повторы и обработка каждого Telegram update отдельно. Для гарантии обработки хранить cursor и статус событий, определить правила retry/dead-letter. Отложенное удаление сообщений вынести из критического пути. Запускать только один poller на токен. Webhook сам по себе не устраняет эти проблемы.

Источник значения scheduler по умолчанию: [Spring Boot 3.5](https://docs.spring.io/spring-boot/3.5/reference/features/task-execution-and-scheduling.html).

### 5. Рост памяти и диска — высокий приоритет длительной работы

`TelegramBotService.java:23,141–147`, `MaxBotService.java:24,159–165`: карты `messages` не имеют TTL или верхней границы. Пользователь, не закончивший выбор, оставляет записи; повторные `/start` увеличивают набор сообщений.

`application.properties:10`, `logback-spring.xml`, `deploy/app.env.example`: `APP_LOG_HISTORY_DAYS=0` сохраняет архивы бессрочно. `maxFileSize=10MB` ограничивает один файл, а не суммарный диск. Логи также попадают в journal.

Исправление: bounded cache/TTL для сообщений, ограничение количества на пользователя; retention 14–30 дней, общий лимит архивов и ограничение journald. Контроль свободного диска обязателен. Даже 1 ГБ логов в сутки заполняет небольшой диск за несколько недель.

## Решения, которые нужно принять

### Публичность расписания

`PublicApiController.java:35–46` публикует данные любой группы без авторизации. `miniapp.js` принимает groupId и start_param, затем читает публичный API. Подпись initData защищает только определение сохранённой группы пользователя, не весь доступ к расписанию.

Если расписание открыто — это допустимая архитектура. Зафиксировать публичность ФИО преподавателей, аудитории и расписания. Если доступ разрешён только студентам, нужна серверная проверка подписи и прав для каждого защищённого ресурса; проверка одного launch endpoint недостаточна.

`findGroup` и запрос расписания не проверяют `active`, поэтому известный ID неактивной группы тоже работает. Скрытие из списка не является контролем доступа. Определить ожидаемое поведение и проверить его тестом.

### Домашняя инфраструктура

Один сервер, один диск, питание и домашний интернет образуют единую точку отказа. Для некритичного расписания это может быть приемлемо. Нужны UPS, автозапуск, backup вне сервера и внешний мониторинг. Если требуется непрерывная доступность, одного домашнего узла недостаточно.

## Средний приоритет

- `SecurityConfig.java:46`: неизвестные маршруты разрешены через `anyRequest().permitAll()`. Лучше разрешить публичные маршруты явно и закрыть остальные. Особенно перед добавлением Actuator.
- CSP Mini App ограничивает только `frame-ancestors`. Нет `script-src`, `object-src`, `base-uri`. Полную CSP внедрять с учётом MAX Bridge и проверкой в обоих мессенджерах.
- Часть одиночных методов каталога не проверяет пустые имена/длину как bulk-методы. Ошибки БД могут попасть в flash message администратора через `e.getMessage()`. Возвращать контролируемые сообщения и 400/404/409 вместо технических исключений.
- Нет `@Version`: параллельные изменения расписания могут перезаписать друг друга. Нет ограничения повторяющихся/пересекающихся занятий. Выбрать нужные бизнес-правила.
- EAGER-связи загружают каталог вместе с сущностями. Измерить SQL и планы до рефакторинга: наличие EAGER само по себе не доказывает N+1.
- Нет метрик, аудита административных изменений и специализированной readiness/liveness. Проверка `/api/public/levels` подтверждает доступность одной операции БД, но не ботов и всего приложения.
- `UgkScheduleApplicationTests` проверяет `assertTrue(true)`. Это не проверка запуска приложения. Остальные unit/WebMvc tests полезны, но не заменяют интеграционные тесты PostgreSQL/Flyway.
- В GitHub Actions JavaScript-тесты не запускаются. Нет отдельного CI для pull request, SCA и проверки секретов.
- Actions указаны тегами `@v5`, а не полными SHA. Для доверенного deploy фиксировать проверенные SHA и обновлять их через Dependabot. [GitHub: безопасное использование Actions](https://docs.github.com/en/actions/reference/security/secure-use).
- Деплой перезапускает один экземпляр, поэтому имеет downtime. Сохраняется один предыдущий JAR, автоматического отката нет. Flyway-изменения БД откатом JAR не отменяются.

## Что уже сделано хорошо

- Пароли администратора хранятся через BCrypt. Административные маршруты требуют ADMIN.
- Обычные административные формы остаются под CSRF-защитой.
- Валидатор initData проверяет HMAC, timestamp, повторяющиеся параметры и положительный user ID. Сравнение HMAC constant-time. Токены Telegram/MAX разделены.
- Алгоритм соответствует опубликованной схеме [Telegram](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app) и [MAX](https://dev.max.ru/docs/webapps/validation). Реальные launch data в этой проверке не использовались.
- Пользовательский текст расписания экранируется перед innerHTML. Название группы выводится через textContent.
- Используются Spring Data JPA и параметризованные производные запросы; явной сборки SQL из пользовательского ввода в проверенном коде нет.
- Flyway версионирует схему; Hibernate validate; open-in-view отключён. Есть FK, unique constraints и индекс расписания.
- Ошибки API не публикуют stack trace. Request logging не пишет query/initData; бот скрывает token в сообщениях своего catch.
- systemd запускает непривилегированного пользователя, привязывает Java к loopback, включает sandbox и ограничивает heap. Nginx передаёт X-Forwarded-*.
- SSH deploy проверяет host key; GITHUB_TOKEN только contents:read; credentials checkout не сохраняются.
- Дополнительный CA используется только HTTP-клиентом MAX; TLS/hostname verification не отключены.

## Теоретическая нагрузка

### Веб и PostgreSQL

У приложения простой сценарий: загрузка HTML/JS/CSS, затем название группы и недельное расписание. По прямому groupId это два API-запроса. При запуске без groupId добавляется POST для определения сохранённой группы. Это число HTTP-запросов, не число SQL-запросов.

Примеры среднего API RPS:

- 500 студентов открывают страницу за 5 минут: примерно 3.3–5 API-запросов/с.
- 2000 студентов за 5 минут: примерно 13.3–20 API-запросов/с.
- 1000 студентов за 10 секунд: примерно 200–300 API-запросов/с.

Статика, TLS, повторные открытия и боты добавляют нагрузку. Число студентов в базе не равно числу одновременных запросов.

**Первые два сценария выглядят реалистичными кандидатами для небольшого сервера, но не являются измеренной гарантией.** Третий требует нагрузочного теста и, вероятно, кэширования открытого расписания/каталога.

Размер каталога невелик. Например, 200 групп × 60 занятий дают 12000 строк расписания. Индекс `(group_id, day_of_week, start_time)` поддерживает основной запрос. Ответ возвращает все записи группы без pagination/верхней границы. EAGER-связи добавляют работу; точное число SQL измерить.

При предположении 10 соединений пула и среднего удержания соединения 20 мс арифметический предел равен 500 операций/с; при 100 мс — 100. Это лишь расчёт пула, не пропускная способность системы: CPU, сериализация, SQL, ожидания и сеть снижают предел. Нужно измерять время удержания соединения и pending connections. Не увеличивать pool без данных.

Домашний upload может стать первым ограничением. При 20 Мбит/с теоретический бюджет около 2.5 МБ/с. Ответ 20 КБ даёт около 125 ответов/с до учёта TLS, статики и прочего трафика. При 50 КБ — около 50. Фактические размеры и upload нужно измерить.

### Боты

Главное ограничение — последовательные внешние HTTP-запросы, не PostgreSQL. Если событие требует двух запросов по 300 мс, один обработчик выполняет около 1.7 события/с до пауз polling и запросов БД. Это пример при выбранной задержке, не замер MAX/Telegram.

Удаление 10 сообщений MAX добавляет минимум 9 × 550 мс = 4.95 с плюс сеть. Сейчас в это время общий scheduler задерживает оба бота. При массовом первом выборе группы задержка может вырасти до минут.

Горизонтально размножать текущий JAR с одинаковыми токенами нельзя: pollers конфликтуют, курсоры и карты находятся в памяти. Для роста нагрузки сначала отделить бот-обработку, устойчивую очередь и идемпотентность; затем решать вопрос реплик.

### Стартовые ресурсы и проверка

Рабочая гипотеза: отдельная VM/машина с 2 CPU, 4 ГБ RAM, SSD и хотя бы 20 ГБ свободного места, Java heap 512 МБ. Это исходная конфигурация для измерений. JVM использует память вне heap; PostgreSQL и ОС тоже требуют RAM. 2 ГБ допустимы для пилота после контроля RSS, swap и пиков.

На staging с реалистичными данными:

1. Измерить API при 10, 25, 50, 100 RPS, затем короткий burst 200 RPS. Каждый шаг 5–10 минут.
2. Смешать название группы, расписание и launch endpoint. Подписанные данные использовать только тестовые, не production tokens.
3. Отдельно проверить несколько одновременных сценариев ботов с ограниченными скоростью платформы и задержками; не спамить пользователей.
4. Отдельно прогнать 24-часовой soak с незавершёнными выборами группы. Следить за heap и ростом maps.
5. Измерить p50/p95/p99, ошибки, CPU/RSS/GC, DB pool wait, SQL, IO, upload, размер ответов и время от события бота до ответа.
6. Начальные критерии: API p95 < 500 мс на целевой устойчивой нагрузке, 5xx < 0.1%, запас CPU/RAM/канала минимум 30%, память не растёт неограниченно. Это предложенные критерии, их нужно согласовать с задачей.
7. После результата выбрать рабочий предел с запасом и настроить rate limits. При bursts уменьшить число SQL/кэшировать только открытые GET; не кэшировать initData, login и административные ответы.
